# The Wire Record Format (Working Draft 0.9.4)

Status: draft. Audience: implementers of ingest tools in this repository.

This document describes the on-disk wire format used by the ingest tools. Sections 1 through 3 are background. Section 4 contains the first normative rules. Section 6 contains the escaping rules. Section 9 is the normative summary and is the section most implementers should read last.

## 1. Introduction

The wire format exists so that small records can be moved between tooling without a schema registry. A document is a plain UTF-8 text stream. A reader turns the stream into records; a writer turns records back into a stream. The two directions are inverses on canonical input, which is what makes the format useful for fixtures and snapshots.

### 4.2 Normative: record boundaries

**RULE-1.** A record is one physical line of the document. A line that is empty or that contains only whitespace is not a record and MUST be skipped. This includes the final newline at end of file, so a document whose last line ends with a newline does not produce an extra empty record.

**RULE-2.** Keys are case-insensitive and MUST be stored lower-cased. A key that appears more than once inside the same record is malformed: `parse` MUST raise `ValueError`. The comparison for duplicates happens after lower-casing, so `Key` and `key` in one record are the same key and MUST be rejected.

### 6.3 Escaping motivation

A value may need to contain the characters that the format uses structurally. Rather than quote whole values, the format reserves the backslash as an escape character. The rules are intentionally tiny so that an implementation can be written in a few lines.

Escaping is interpreted before the record is split into pairs. This ordering matters: if an escaped pipe were treated as a separator first, a value containing a pipe could not round-trip.

### 6.4 Normative: value escaping

**RULE-3.** Inside a value, the two-character sequence backslash-pipe denotes a literal pipe, and backslash-backslash denotes a literal backslash. The escape MUST be interpreted before pairs are split, so an escaped pipe never separates two pairs. When writing a value, `render` MUST escape every literal backslash first and then every literal pipe, so that the result can be parsed back to the same value. A key is not a value and MUST NOT contain escapes.

**RULE-4.** A value that ends with a lone backslash is malformed, and a backslash followed by any character other than a pipe or a backslash is malformed. In both cases `parse` MUST raise `ValueError`. Readers MUST NOT silently drop an unknown escape.

## 9. Normative summary

This section restates the remaining obligations. It is normative. If any earlier section appears to conflict with this summary, this summary wins.

**RULE-5.** A pair without an equals sign is malformed and `parse` MUST raise `ValueError`. A pair whose key is empty is malformed and `parse` MUST raise `ValueError`. Only the first equals sign in a pair separates the key from the value; the value itself may contain further equals signs.

**RULE-6.** The reserved key `seq` MUST hold exactly four decimal digits. A value that is shorter than four characters, longer than four characters, or that contains a character outside `0`-`9` is malformed and `parse` MUST raise `ValueError`. Leading zeros are significant and MUST be preserved in the parsed value. `seq` is validated after unescaping.

**RULE-7.** `render(records)` returns canonical text: one record per line, pairs joined by a pipe, keys in insertion order, values escaped per RULE-3, and one trailing newline. `render([])` returns the empty string. For every accepted document `x`, `parse(render(parse(x)))` equals `parse(x)`, and for every canonical document `x`, `render(parse(x))` equals `x`.

### 9.1 Worked canonical examples

```
a=1|b=2
seq=0042|note=left\|right
```

The second example shows an escaped pipe inside the value of `note`. After parsing, the value is the seven-character text `left|right`; after rendering it again, the pipe is escaped once more.
